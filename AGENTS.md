# ProcessGraphQL Agent Guide

This document is for AI agents (and humans) working on the ProcessGraphQL codebase. It outlines the project structure, development workflows, and common tasks.

## Project Overview

**ProcessGraphQL** is a ProcessWire module that seamlessly integrates GraphQL into a ProcessWire application. It allows users to serve a GraphQL API of their existing content without modifying structure.

- **Stack:** PHP (ProcessWire), Node.js (Dev tooling).
- **Core Library:** `webonyx/graphql-php`.
- **Key Features:**
    - Schema generation based on ProcessWire Templates and Fields.
    - Access Control (respects ProcessWire permissions).
    - GraphiQL interface.
    - Extensible via Hooks (`getQueryFields`, `getMutationFields`).

## Directory Structure

- `src/`: Core PHP source code (PSR-4 `ProcessWire\GraphQL\`).
- `test/`: PHPUnit tests.
- `ProcessGraphQL.module`: Main module file (ProcessWire entry point).
- `ProcessGraphQLConfig.php`: Module configuration logic.
- `graphiql/`: GraphiQL interface assets.
- `vendor/`: Composer dependencies.

## Common Tasks

Check `src/Type/Fieldtype/` to see existing implementations.

- Register it in the main schema generation logic.

### 2. Debugging

## Conventions
- Client selectors always go through `SelectorType::parseValue()`. It rejects
  visibility changing selector fields (`include`, `status`, `check_access`, ...)
  and limits results to legal, viewable templates and `maxLimit`.
- Mutations re-check permissions on the target page; never trust the template
  a mutation was generated for alone.
- Avoid N+1: collect IDs with `PagesBuffer::add()` and resolve with a
  `GraphQL\Deferred` that loads the whole batch once (see `PageType`,
  `FieldtypeFile`, `FieldtypePage`, `FieldtypeRepeater`).
- No static state. Everything of one execution lives in `ProcessWire\GraphQL\Context`
  (created by `$module->createContext()`, passed to graphql-php as `contextValue`):
  ProcessWire instance, module, `permissions`, `buffer` (PagesBuffer), `types`
  (TypeRegistry), parsed selectors and batch loaded file rows.
- Type builders take the context as first argument (`PageType::type($context, $template)`)
  and register types via `$context->types->type($name, fn() => ...)`; define `fields` as
  closures. Resolvers use their third argument `Context $context`, never `Utils::pages()` etc.
- The schema is built per context (`Schema::build($context)` / `$module->getSchema($context)`),
  because it depends on the user's permissions.
- Third-party fieldtypes (`GraphQL<Fieldtype>` modules) keep their static, context free
  contract: `getType(Field)`, `getInputType(Field)`, `setValue(Page, Field, $value)`.

## Known Issues / Todo
- **Schema caching:** Deliberately not done. The schema is built per execution, which
  costs well under 1ms and no database queries (types and enum values are lazy). It
  holds closures bound to the Context, so it cannot be serialized between requests; an
  in-memory cache per role set would only help long running workers and would need
  invalidation on template, field and permission changes.
